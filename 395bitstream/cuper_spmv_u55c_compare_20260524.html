结论

65,536 TAPA 本次稳定完成的最大 N
1,228,045 no-TAPA single SpMV 与 full-PCG 代理跑通的最大 N
50.6x N=65,536 时 TAPA kernel 平均时间优势
169.13 ms full-PCG 初始 SpMV 代理跑完整 thermal2 的 kernel 时间

在已正常返回的数据点上，TAPA Cuper SpMV 明显更快；到 thermal2_n65536， TAPA 平均 0.156 ms，no-TAPA 平均 7.884 ms。 但 TAPA host 在 thermal2_n131072 和 thermal2_n262144 上出现 “XRT 显示 CU 已 IDLE，但 host 进程不返回”的等待问题，所以本次没有可靠的 TAPA 百万级结果。

no-TAPA 独立 SpMV 路径稳定跑完从 N=16 到完整 thermal2 的全部数据点；大数据段 kernel 平均时间随 nnz 近似线性增长，吞吐维持在约 0.11 GFLOP/s。 旧版 full-FPGA-PCG bitstream 也能跑到完整 thermal2，但当前 host 只暴露整段 cuper_pcg_control_kernel 时间，不能直接读出单独 SpMV 计时。

测试口径

命令模式

两版都使用 --spmv-only，输入向量固定为数据集的 b.txt，CPU Dataset::spmv 作为校验基准。

除 TAPA N=16 用 1 次受控 smoke 外，其它成功 SpMV 数据点都跑 SPMV_REPEATS=3。

full-PCG 旧版没有 --spmv-only，使用 TAU=1e100 MAX_ITERS=1 让 kernel 完成初始 A*x0 与 r/z/p 初始化后立刻收敛返回。

make run-cuper-tapa-spmv TARGET=hw \
  DATASET=data/suitesparse/Schmid/csr/thermal2_n65536 \
  BITFILE=395bitstream/cuper-tapa-spmv-u55c-20260522.xclbin \
  SPMV_REPEATS=3 DIFF_TOL=1e-1

make run-cuper-notapa-spmv-xrt TARGET=hw \
  DATASET=data/suitesparse/Schmid/csr/thermal2_n65536 \
  BITFILE=395bitstream/cuper-notapa-spmv-u55c-20260524.xclbin \
  SPMV_REPEATS=3 DIFF_TOL=1e-1

make run-cuper-control-xrt TARGET=hw \
  DATASET=data/suitesparse/Schmid/csr/thermal2_n65536 \
  BITFILE=395bitstream/cuper-notapa-pcg-fpga-u55c-20260522.xclbin \
  TAU=1e100 MAX_ITERS=1 DIFF_TOL=1e-1

计时含义

spmv_avg 是报告里用于比较的主指标。

no-TAPA 的 spmv_avg 来自 host 端包住 run.wait() 的 wall time；xrt_setup、BO setup、H2D/D2H 单独列出。

TAPA 的 spmv_avg 来自 tapa::invoke 返回的 kernel 时间；TAPA runtime 打印的 load/opencl 日志不直接计入这个值。

full-PCG 代理的 pcg_proxy_ms 来自 [timing-ms] kernel=...，包含初始 Cuper packed SpMV 和向量初始化，不能和 single-SpMV 的 spmv_avg 当作完全同口径指标。

大数据 TAPA 未返回时，板卡动态区显示 Cuper:Cuper_1 为 IDLE，因此报告把它归为 host/TAPA runtime 返回路径问题，而不是计算错误。这个现象发生在 --spmv-only，不是 host 端 PCG 全流程被砍掉后才进入的路径。

每版细节

TAPA cuper-tapa-spmv-u55c-20260522

优势：小到中等规模的成功数据点上，平均 kernel 时间明显低于 no-TAPA；到 N=65,536 时达到 5.61 GFLOP/s。

问题：N=131,072 和 N=262,144 触发硬件调用后，xbutil examine --report dynamic-regions 显示 Cuper:Cuper_1 已经 IDLE，但 host 进程没有返回。已手动停止并标记为 stopped_after_idle_wait。

判断：bitstream 本身能跑，但当前 host/TAPA runtime 大矩阵返回路径需要继续查。

no-TAPA cuper-notapa-spmv-u55c-20260524

优势：从 N=16 到完整 thermal2 全部稳定返回，校验误差均小于 DIFF_TOL=1e-1。

瓶颈：kernel 平均时间随规模增长到完整 thermal2 的 146.27 ms，大数据段吞吐基本维持在约 0.11 GFLOP/s。

判断：更适合作为稳定、可拉通百万级数据的当前 no-TAPA baseline。

full-PCG cuper-notapa-pcg-fpga-u55c-20260522

这版是上一版全流程 FPGA-PCG：kernel 内部包含初始 Cuper packed SpMV、PCG 控制、dot、向量更新和收敛判断。当前 host 没有 --spmv-only，也没有 kernel 内分段计时寄存器，所以不能单独抽出 SpMV 时间。

本次用 TAU=1e100 MAX_ITERS=1 跑代理：所有数据点都在 iter=0 返回 converged，完整 thermal2 的 kernel 时间为 169.13 ms。这说明百万级数据本身和 no-TAPA full-PCG bitstream 可以返回，TAPA 百万级不返回更可能在 TAPA host/runtime 返回路径。

Launcher / Makefile 检查

检查时发现 no-TAPA SpMV 硬件运行路径原来不会使用用户传入的 BITFILE： run-cuper-notapa-spmv-xrt 和 run-cuper-notapa-pcg-xrt 总是强制找 cuper-pcg-notapa/hw/cuper_packed_spmv_kernel.xclbin。 这会导致 launcher 不能直接跑 395bitstream/cuper-notapa-spmv-u55c-20260524.xclbin。

本次已修正 Makefile 为 $(or $(BITFILE), default) 逻辑；run-cuper-control-xrt 也支持传入旧版 full-PCG bitstream。并在 scripts/launcher.py 的 no-TAPA 硬件菜单里加入 bitstream 路径输入，默认指向 395bitstream/cuper-notapa-spmv-u55c-20260524.xclbin。

验证：python3 -m py_compile scripts/launcher.py 通过，make -n 已确认命令会把归档 bitstream 传给 host。

后续建议

TAPA 路线的 kernel 吞吐很强，优先查 host/cuper_tapa_pcg_main.cpp 里 大 batch 场景的 tapa::invoke 返回路径、buffer size、aligned mmap 生命周期和 TAPA runtime 对大 mmap 的同步行为。 由于卡住发生在 --spmv-only 路径，host 侧 PCG 全流程被砍掉不是主要嫌疑。 当前失败阈值在 N=65,536 与 N=131,072 之间。

no-TAPA 路线已能拉通百万级数据，可作为继续比较 PCG 全流程和端到端预处理开销的稳定基线。 如果只看单次 SpMV kernel，当前 no-TAPA 大数据吞吐约 0.11 GFLOP/s，和 TAPA 已完成点差距较大。
