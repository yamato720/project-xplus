计时含义

spmv_avg 是报告里用于比较的主指标。

no-TAPA 的 spmv_avg 来自 host 端包住 run.wait() 的 wall time；xrt_setup、BO setup、H2D/D2H 单独列出。

TAPA 的 spmv_avg 来自 tapa::invoke 返回的 kernel 时间；TAPA runtime 打印的 load/opencl 日志不直接计入这个值。

full-PCG 代理的 pcg_proxy_ms 来自 [timing-ms] kernel=...，包含初始 Cuper packed SpMV 和向量初始化，不能和 single-SpMV 的 spmv_avg 当作完全同口径指标。

新 TAPA full-PCG 的 tapa_pcg_init_ms 和 tapa_pcg_1iter_ms 均来自 [timing-ms] kernel_reported=...；分段时间来自 [stage-ms]，本 demo 需要把 iter recv 和 dot_p_ap 合看为 AP path。host wall time 另含 xclbin load/runtime 同步开销，不用于总表。

大数据 TAPA SpMV 未返回发生在 --spmv-only 路径，不是 host 端 PCG 全流程被砍掉后才进入的路径；本轮表现为 thermal2_n262144 和完整 thermal2 180s 超时。 timed-debug 版 TAPA full-PCG 已能返回到 thermal2_n262144，且 stage counter 有效；完整 thermal2 两种 PCG 口径重测时控制寄存器都保持 0x0 未完成。

每版细节

TAPA cuper-tapa-spmv-u55c-20260522

优势：小到中等规模的成功数据点上，平均 kernel 时间明显低于 no-TAPA；到 N=131,072 时达到 7.88 GFLOP/s。

问题：N=262,144 和完整 thermal2 在本轮 180s 限时内没有返回。

判断：bitstream 小中规模路径可用，但当前 host/TAPA runtime 大矩阵返回路径仍需要继续查。

no-TAPA cuper-notapa-spmv-u55c-20260524

优势：从 N=16 到完整 thermal2 全部稳定返回，校验误差均小于 DIFF_TOL=1e-1。

瓶颈：新版归档 xclbin 实际是 cuper_packed_spmv_4ch_kernel，kernel 平均时间随规模增长到完整 thermal2 的 200.62 ms，大数据段吞吐基本维持在约 0.08 GFLOP/s。

判断：更适合作为稳定、可拉通百万级数据的当前 no-TAPA baseline。

full-PCG cuper-notapa-pcg-fpga-u55c-20260522

这版是上一版全流程 FPGA-PCG：kernel 内部包含初始 Cuper packed SpMV、PCG 控制、dot、向量更新和收敛判断。当前 host 没有 --spmv-only，也没有 kernel 内分段计时寄存器，所以不能单独抽出 SpMV 时间。

本次用 TAU=1e100 MAX_ITERS=1 跑代理：所有数据点都在 iter=0 返回 converged，完整 thermal2 的 kernel 时间为 169.19 ms。这说明百万级数据本身和 no-TAPA full-PCG bitstream 可以返回，TAPA 百万级不返回更可能在 TAPA host/runtime 返回路径。

TAPA full-PCG cuper-tapa-pcg-fpga-u55c-20260525

Launcher / Makefile 检查

检查时发现 no-TAPA SpMV 硬件运行路径原来不会使用用户传入的 BITFILE： run-cuper-notapa-spmv-xrt 和 run-cuper-notapa-pcg-xrt 总是强制找 cuper-pcg-notapa/hw/cuper_packed_spmv_kernel.xclbin。 这会导致 launcher 不能直接跑 395bitstream/cuper-notapa-spmv-u55c-20260524.xclbin。

本次已修正 Makefile 为 $(or $(BITFILE), default) 逻辑；run-cuper-control-xrt 也支持传入旧版 full-PCG bitstream。并在 scripts/launcher.py 的 no-TAPA 硬件菜单里加入 bitstream 路径输入，默认指向 395bitstream/cuper-notapa-spmv-u55c-20260524.xclbin。

验证：python3 -m py_compile scripts/launcher.py 通过，make -n 已确认命令会把归档 bitstream 传给 host。

后续建议

TAPA 路线的 kernel 吞吐很强，优先查 host/cuper_tapa_pcg_main.cpp 里 大 batch 场景的 tapa::invoke 返回路径、buffer size、aligned mmap 生命周期和 TAPA runtime 对大 mmap 的同步行为。 由于卡住发生在 --spmv-only 路径，host 侧 PCG 全流程被砍掉不是主要嫌疑。 当前失败阈值在 N=131,072 与 N=262,144 之间。

新 TAPA full-PCG 路线的当前 demo 已把可返回规模拉到完整 thermal2；timed-debug 数据显示 full-PCG 内部 AP path 不是唯一瓶颈。2026-05-28 demo-only 测试中，完整 thermal2 1iter 的 update_xr=486.83 ms、update_p=402.64 ms、 dot_p_ap=132.74 ms，下一步优先查 packed AP/P 后续消费路径和 FP64 controller 更新路径。

no-TAPA 路线已能拉通百万级数据，可作为继续比较 PCG 全流程和端到端预处理开销的稳定基线。 如果只看单次 SpMV kernel，当前 no-TAPA 4ch 大数据吞吐约 0.08 GFLOP/s，和 TAPA 已完成点差距较大。
