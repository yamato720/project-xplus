# 2026-05 月报

## 本月目标

本月是 Project-XPlus / Cuper TAPA PCG 优化工作的第一阶段，目标不是直接替换标准 bitstream，而是先把可验证的优化边界和测试闭环建立起来。

1. 建立 `cuper-tapa-pcg` full-PCG 的持续优化主线，重点从单纯 SpMV 本体转向 `CuperPcg(...)` 内部的 controller、dot、update 和向量访问路径。
2. 补齐 single SpMV demo，用于拆分 full-PCG 内嵌 SpMV 和 PCG controller/service 的边界，确认问题到底来自 SpMV 本体还是周边控制路径。
3. 形成 demo bitstream 的构建、同步、归档和上板测试纪律：demo 不直接替换标准版，只有性能和功能都确认后才考虑晋级。
4. 完善版本记录和测试文档，确保每个 xclbin 的 UUID、SHA256、clock、测试日志、成功边界和性能结论都能追溯。

## 进展同步

### 1. single SpMV 边界验证

本月先补了 `CuperPcgSpmv(...)` single SpMV demo。第一版尝试抽出 full-PCG service SpMV，在 `thermal2_n16` 上板 smoke 中出现 180s timeout，日志停在 `after ReadFromDevice before Finish`，因此未晋级。

随后将 `CuperPcgSpmv(...)` 改回 Cuper-compatible one-shot 图，保留历史 kernel/demo 入口，但内部复用 `Cuper(...)` 同款 SpMV task graph，不再引入 PCG service/control 外壳。该版本已完成硬件构建和 demo-only 上板测试，并已归档到：

```text
bitstream_archive/2026-05-29-tapa-pcg-spmv-demo-candidates/
```

关键结论：

- one-shot demo 能跑通 `thermal2_n16`、`thermal2_n65536`、`thermal2_n131072`、`thermal2_n262144` 和完整 `thermal2`；
- 完整 `thermal2` single SpMV `spmv_avg=1.781541 ms`，GFLOP/s 为 `9.6325`，diff 通过；
- 共同成功点上比当前 standalone Cuper SpMV 标准记录略慢，但成功边界更好；
- single SpMV 结果只能作为回归基线，不能直接证明 full-PCG 性能提升。

### 2. full-PCG packed feed / AP / timing 主线

full-PCG 主线围绕 `CuperPcg(...)` 做了多轮实验。主要改动包括：

- 新增 `X_spmv` / `P_spmv` packed `float_v16` 输入，避免 controller 从 `double X/P` 逐元素打包；
- 新增 `AP_spmv` packed 输出，减少 AP 拆包写回开销；
- 将 `p^T AP` 合入 `iter_spmv_stream` 接收路径；
- 将 `B/M_inv/X/R/Z/P` 主状态从标量 `double` mmap 改为 packed `double_v8` mmap；
- host ABI 更新到 28 个 memory arg，同时保留 `--legacy-abi` 用于旧标准 bitstream；
- 更新 stage metrics 口径，区分 packed memory packet work 和真实 stage cycle/ms。

当前 packed timing demo 已完成 `hw` 构建和 demo-only 上板测试：

```text
395bitstream/cuper-tapa-pcg-fpga-u55c-20260531-demo.xclbin

SHA256: a8df40e1bf21774c7608c329fd591012b84744a18dcf4e8b0dd36672d64ccf72
DATA/KERNEL/HBM: 172/500/405 MHz
```

上板结果显示，`thermal2_n16`、`thermal2_n65536`、`thermal2_n131072`、`thermal2_n262144` 和完整 `thermal2` 的 init-only / 1iter 均返回，direct ctrl 均为 `0x4 -> 0xe`，数值校验通过。

完整 `thermal2` 1iter 关键数据：

| 指标 | 数值 |
| --- | ---: |
| `kernel_reported` | `944.1232 ms` |
| `controller_total` | `920.2593 ms` |
| `init_spmv + iter_spmv_recv_dot` | `189.3382 ms` |

结论是：packed 端口和 SpMV 周边路径已经有改善，但 full-PCG 主要瓶颈仍在 controller 内的向量阶段串行、FP64 reduction、HBM 往返和 lane-wise compute/store，而不是 raw SpMV 本体。

### 3. controller-split 与 reduction 实验

本月完成了 controller-split demo 的构建、demo-only 测试和归档。该实验把 `dot_p_ap` 合入 AP 接收路径，并拆分 `update_xr` / `update_p` 的 compute 与 store。归档位置：

```text
bitstream_archive/2026-05-31-tapa-pcg-controller-split-demo/
```

controller-split demo 的完整 `thermal2` 1iter 为 `954.0779 ms`，比上一轮 II=1 demo 的 `1767.8254 ms` 明显改善。补跑 full-run 后，`thermal2_n16` 到 `thermal2_n262144` 均能多轮收敛；完整 `thermal2` 在禁用 host 60s 超时后约 490s 仍未完成，按要求停止并记录。

此外，在 `main` 工作区继续做了较小范围的 reduction 实验：

- `init_zp` / `update_z` 的 `rz/rr` FP64 reduction 改成 8-bank 累加；
- `thermal2_n16` 与 `thermal2_n1024` 的 1iter 软件仿真通过；
- HLS 报告中 `init_zp` packet loop 从 II=5 降到 II=4，`update_z` packet loop 从 II=5 降到 II=2；
- 对 `p^T AP` 做同类 banked reduction 会把 `iter_spmv_stream` 拉到 II=11，已撤回。

## 下月计划

1. 继续以 full `CuperPcg(...)` 为主优化对象，暂不把 single SpMV 作为主要提速方向；single SpMV 只作为成功边界和回归基线。
2. 优先处理 controller/vector 阶段瓶颈，重点关注 `update_xr`、`update_z`、`update_p`、`init_zp`、AP stream 与 HBM 往返。
3. 对 worker/service 拆分路线做可布线性评估：若低侵入版本能完成 bitstream，再补 demo-only 上板测试；若仍受拥塞限制，应收敛改动范围，避免继续扩大 task/stream 复杂度。
4. 补强 full-run 测试：对有效 demo 至少覆盖 `thermal2_n16` 到 `thermal2_n262144` 的多轮收敛；完整 `thermal2` 视运行时间和用户要求决定是否补测。
5. 更新 HTML/Markdown 报告时，保持 stage counter 语义清晰：当前 `iter_spmv` 已包含 `p^T AP`，应标注为 `iter recv + dot`，避免和旧口径混用。
6. 只有在 demo-only 上板数据明确优于当前标准版且功能边界稳定后，才更新正式 `source.diff` 或考虑标准 bitstream 晋级。

## 复盘总结

本月最重要的收获是把优化边界理清了：full-PCG 的主要瓶颈不再能简单归因于 SpMV 本体。single SpMV one-shot demo 已经证明 Cuper 风格图可以跑通完整 `thermal2`，而 full-PCG 里真正拖慢 1iter 的主要是 controller 内的向量更新、归约和 HBM 访问组织。

从工程流程看，本月也建立了较完整的 demo 纪律：失败版本、历史 UUID、当前 demo、归档 demo 和标准版之间已经分开记录，避免同名 xclbin 被覆盖后测试结论混用。这个做法后续需要继续保持。

当前不足是硬件构建和上板验证成本较高，部分实验在 HLS 层面看起来有效，但到 route 或板上性能时会暴露拥塞、频率下降或全局收益不足的问题。下月应减少大范围并行拆分的盲试，更多采用“小改动、可解释 metrics、可上板验证”的节奏推进。
