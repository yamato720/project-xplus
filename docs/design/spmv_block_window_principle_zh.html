Project-XPlus 分块与滑动窗口 SpMV 原理

这份文档说明当前 pcg_control_kernel 里的 SpMV 为什么要同时使用 4x4 block/bitmap 和 x 滑动窗口，以及它们如何在数学上仍然等价于 y = A * x。

实现位置：kernels/pcg_control_kernel.cpp 公共结构：include/cg_common.hpp 窗口长度：kSpmvWindowSize = 512 块大小：kSpmvBlockSize = 4

1. 要解决的问题

稀疏矩阵向量乘 SpMV 的核心公式很简单，但在 FPGA 上困难主要来自访存： 矩阵非零元按稀疏结构访问，x[col] 的列号通常不连续。如果每个非零元都直接随机读 HBM， 流水线很容易被访存延迟拖住。

y_i = sum_j A_ij * x_j
不再缓存完整 x 完整 x_local[n] 会让片上 BRAM 随问题规模增长。当前只缓存固定长度窗口。
A 也按 window 重排 host 把 CSR 转成 4x4 block/bitmap 后，再按 x-window 组织 A 的 block 子流。
按列窗口累加 y 一次 A*x 被拆成多个 A[:, window] * x[window] 的部分和。

2. 4x4 block/bitmap 分块格式

host 仍从原始 CSR 数据集读取矩阵，但会先把矩阵按 4 行、4 列切成小块。 第 br 个 block row 覆盖原矩阵行：

row = 4 * br + local_r, local_r in {0, 1, 2, 3}

第 bc 个 block column 覆盖原矩阵列：

col = 4 * bc + local_c, local_c in {0, 1, 2, 3}

compact 存储

这个 block 不保存完整 16 个 double，而是用 16-bit mask 记录哪些位置非零， 再把非零值按 row-major 顺序紧凑放进 values[]。

pos = local_r * 4 + local_c mask bit(pos) = 1 表示该位置非零 values[] = [a, b, c, d, e]
a_win_row_ptr window-major block row 指针。第 w 个 window、第 br 个 block row 的区间由 a_win_row_ptr[w][br] 到 a_win_row_ptr[w][br+1] 给出。
a_win_col_idx 每个 windowed 非零 4x4 block 的绝对 block column。真实列号仍需要加上块内 local_c。
a_win_blocks 按 window 顺序排列的 block payload，包括 compact values 和 16-bit occupancy mask。
y[4*br + local_r] += block(local_r, local_c) * x[4*bc + local_c]
关键点： 这里的分块不是改变数学矩阵，只是改变存储和遍历顺序。所有非零值仍然按原来的 A[row, col] 参与乘加。

3. 滑动窗口的数学等价变换

当前窗口长度固定为 512。kernel 每次只把一段 x 搬到片上 BRAM：

W_t = [t * 512, min((t + 1) * 512, n)) x_window = x[W_t]

完整 SpMV 可以按列窗口拆成部分和：

y = A * x = A[:, W_0] * x[W_0] + A[:, W_1] * x[W_1] + A[:, W_2] * x[W_2] + ...

数学上等价

每个非零项 A_ij * x_j 的列 j 只会落入唯一一个窗口。 所有窗口的贡献加起来，正好覆盖完整的 sum_j。

硬件上固定片上容量

片上只保留 512 个 double 的 x_window。 使用 ping-pong 后是两份窗口缓存，约 2 * 512 * 8 = 8192 字节。

为什么窗口大小要是 4 的整数倍： block column 的宽度是 4。512 % 4 == 0，所以一个 4x4 block column 不会横跨两个 x 窗口。host 可以把每个 4x4 block 精确归到唯一一个 A-window，kernel 不需要拆 block。

5. 单个 row tile/window 如何累加

accumulate_window_tile 处理的是一个列窗口对当前 row tile 的贡献：

y_tile += A[row_tile, window_begin:window_end) * x_window

每个 block row

  1. 用 row_ptr_base = window_id * (num_block_rows + 1) 找到当前 window 的 row pointer 区域。
  2. 只遍历当前 row tile 内的 block row：br = row_tile_begin_br + local_br。
  3. 读取 a_win_row_ptr[row_ptr_base + br] 到 a_win_row_ptr[row_ptr_base + br + 1]。
  4. 如果该 row/window 没有 block，则 y_tile 对应行保持已有部分和。
  5. 不再从 HBM 读回 y，所有 window 的部分和直接累在 BRAM 的 y_tile 中。

每个非零 block

  1. 当前 row pointer 区间已经只包含这个 window 的 block。
  2. 顺序读取 a_win_col_idx[bi] 和 a_win_blocks[bi]。
  3. 按 mask 遍历 block 内非零位置并乘加。
zero_y_tile(y_tile) for each window: load current x_window for each local block row local_br in row_tile: br = row_tile_begin_br + local_br row_ptr_base = window_id * (num_block_rows + 1) block_start = a_win_row_ptr[row_ptr_base + br] block_end = a_win_row_ptr[row_ptr_base + br + 1] for bi in block_start : block_end: bc = a_win_col_idx[bi] block = a_win_blocks[bi] for pos in 0 : 16: if mask bit(pos) == 1: local_r = pos / 4 local_c = pos % 4 global_c = 4 * bc + local_c tile_row = local_br * 4 + local_r y_tile[tile_row] += block_value * x_window[global_c - window_begin] write_y_tile(y, y_tile)
注意： 当前 A 已经按 x-window 分组，所以 kernel 不再对 block row 做二分查找或逐项过滤。 row tile 把多行 y/ap 部分和跨多个 window 留在 BRAM， 每个输出元素在一次 SpMV 中只需要最后写回 HBM 一次。

6. ping-pong 缓冲与 DATAFLOW

当前有两个片上窗口缓存：

data_t x_window_ping[kSpmvWindowSize]; data_t x_window_pong[kSpmvWindowSize]; #pragma HLS BIND_STORAGE variable = x_window_ping type = ram_2p impl = bram #pragma HLS BIND_STORAGE variable = x_window_pong type = ram_2p impl = bram

偶数窗口

使用 ping 作为当前计算输入，同时把下一窗口加载到 pong。

奇数窗口

使用 pong 作为当前计算输入，同时把下一窗口加载到 ping。

compute window t from buffer A load window t+1 into buffer B

两个 helper 函数内部使用 #pragma HLS DATAFLOW，让 HLS 尝试把这两个任务重叠。 这个 DATAFLOW 只覆盖 SpMV 的窗口级 load/compute，不代表整个 PCG 主循环都能 dataflow。

为什么写成两个 helper： Vitis HLS 2022.2 的 DATAFLOW 区域不适合直接放条件执行。 所以代码把 ping 和 pong 分成两个固定任务图：一个固定读 ping 写 pong，另一个固定读 pong 写 ping。

7. 它在 PCG 里的位置

当前 pcg_control_kernel 是单顶层 kernel。SpMV 被调用两类场景：

初始化阶段

ap = A * x0 r0 = b - ap

ap BO 临时承载 ax0。

PCG 主循环

ap = A * p pAp = p^T ap

这里是每轮迭代计算量最大的部分。

PCG 的 alpha、beta、收敛判断和 breakdown 判断仍然有严格标量依赖。 因此当前只在 SpMV 内部做窗口级 dataflow，而不是把完整 PCG 迭代做成无停顿流水线。

8. 当前局限和下一步

当前已经解决的点

  • 不再要求完整 x 放进片上数组。
  • 窗口 BRAM 容量固定，不随 n 线性增长。
  • block 内访问 x_window 命中片上 BRAM。
  • A 的 block payload 已按 x-window 分组，kernel 只读当前 window 的 block 子流。
  • y/ap 的部分和已经按 row tile 暂存在片上 BRAM，跨所有 x-window 累完后再写回。
  • 数值结果仍等价于完整 A*x。

当前还没有解决的点

  • 每个 row tile 都会重新加载所有 x-window；row tile 越小，x-window 重载次数越多。
  • y_tile 是 BRAM read-modify-write 归约目标，同一行多 block 累加会形成真实依赖。
  • 矩阵还没有进一步拆成多 compute worker 并行处理。
  • 当前是 windowed A block stream 版本，不是最终吞吐最优版本。

当前已经生成了按窗口分组的 metadata：

window_ptr[window] window_block_row[entry] window_block_col[entry] window_blocks[entry]

在代码里它落成 a_win_row_ptr / a_win_col_idx / a_win_blocks。 kernel 现在再叠加 row tile，实际计算顺序就是 row tile x column window：固定一批输出行，把所有列窗口贡献累完再写回。
